em_motion是一个常用运动行为模型的控制库

分为2种，一种是云台控制，另外一种是小车控制。这个库主要是数据解算，按照要求控制，硬件部分由外部的驱动实现，并且硬件控制函数以包含函数指针的结构体的方式注入给我们使用。

| 模块           | 文件名            | 核心功能                           |
| :------------- | :---------------- | :--------------------------------- |
| 差速运动学     | `kin_diff.c`      | 输入v,w → 左右轮速；里程计解算     |
| 全向运动学     | `kin_omni.c`      | 全向轮（三轮/四轮）速度分配        |
| 麦克纳姆运动学 | `kin_mecanum.c`   | 麦克纳姆轮速度分配（可单独或共用） |
| 阿克曼运动学   | `kin_ackermann.c` | 自行车模型，转角与速度映射         |
| 梯形规划       | `trapezoidal.c`   | 梯形速度曲线生成                   |
| S型规划        | `s_curve.c`       | S型速度曲线（加加速度限制）        |
| 多项式规划     | `polynomial.c`    | 高阶多项式插值（如五次多项式）     |
| 倒立摆动力学   | `inv_pendulum.c`  | 重力补偿、LQR/PID控制器            |

开发顺序

1. **差速运动学**（最常用底盘）
2. **梯形规划**（最简单轨迹）
3. **阿克曼运动学**（车模常用）
4. **倒立摆动力学**（平衡车）
5. **S型规划**（需要平滑启停）
6. **全向/麦克纳姆**（全向底盘）
7. **多项式规划**（复杂轨迹，如机械臂）

## 关键算法提示

- **差速运动学**
  正解：v = (vr + vl)/2, w = (vr - vl)/L
  逆解：vr = v + w*L/2, vl = v - w*L/2
  里程计积分：x += v*dt*cos(theta), y += v*dt*sin(theta), theta += w*dt
- **阿克曼运动学**
  自行车模型：tan(δ) = L / R，其中 δ 为前轮转角，L 为轴距，R 为转弯半径
  逆解：给定 v, ω → R = v/ω → δ = atan(L/R)
- **全向轮（三轮）**
  常见配置：轮子夹角120°，速度映射矩阵需要根据安装角度推导。
- **梯形规划**
  三段式：匀加速、匀速、匀减速。注意边界条件（位移不够时可能没有匀速段）。
- **S型规划**
  七段式：加加速、匀加速、减加速、匀速、加减速、匀减速、减减速。需处理位移约束。
- **倒立摆控制**
  典型LQR或PD控制器：τ = Kp*(θ_des - θ) + Kd*(0 - θ_dot) + m*g*L*sin(θ)（重力补偿）

## 参考信息

#### 场景 A：两轮平衡车

- **数学本质**：差速驱动 + 倒立摆。
- 文件名
  - `kin_diff.c` (差速运动学：负责左右轮速度解算，里程计计算)
  - `dyn_inverted_pendulum.c` (**核心**：倒立摆动力学模型。包含重力矩计算、惯量补偿、平衡角度控制)
  - *注：平衡车的难点不在运动学，而在动力学。这个文件是你平衡算法的灵魂。*

#### 场景 B：普通两轮/三轮/四轮底盘

- **数学本质**：差速驱动 + 刚体运动。
- 文件名
  - `kin_diff.c` (与平衡车共用同一套运动学模型)
  - `dyn_rigid_body.c` (刚体动力学：处理简单的摩擦力补偿、加速度限制，比平衡车简单得多)

#### 场景 C：阿克曼转向小车

- **数学本质**：自行车模型 / 阿克曼几何。
- 文件名
  - `kin_ackermann.c` (阿克曼运动学：处理前轮转角与后轮差速的关系，防止轮胎打滑)
  - `dyn_vehicle.c` (车辆动力学：如果需要做漂移或高速控制，处理轮胎侧偏特性)

#### 场景 D：全向移动小车

- **数学本质**：全向轮运动学。
- 文件名
  - `kin_mecanum.c` (麦克纳姆轮运动学：全向移动解算)
  - `kin_omni.c` (全向轮运动学)

对于 PTZ，我建议把架构调整为：**规划层 + 驱动层**。

### 1. PTZ 的文件架构设计

PTZ 的数学模型（轨迹规划）是通用的，应该独立出来；差异化的部分封装在驱动层。

#### 第一层：通用规划模型

这是你的核心算法库，与硬件无关。

- `model_trajectory.c`

   

  (或者叫

   

  ```
  planner_interpolator.c
  ```

  )

  - **功能**：这就是我们之前写的梯形/S型曲线规划。输入目标位置、最大速度、加速度，输出当前的**中间插值位置**。
  - **适用性**：这段代码，PWM舵机用得上，步进电机用得上，无刷云台也用得上。**写一次，终身受用。**

#### 第二层：抽象驱动接口

定义统一接口，类似于 Linux 的 VFS（虚拟文件系统）。

- `ptz_interface.h`
  - 定义结构体：`ptz_driver_t`，包含 `init`, `set_angle`, `enable` 等函数指针。

#### 第三层：具体驱动实现

这里才是你担心的“不同型号”区分的地方。按照**控制原理**来命名文件，而不是电机型号。

| 电机类型     | 推荐文件名             | 核心逻辑                                                     |
| :----------- | :--------------------- | :----------------------------------------------------------- |
| **PWM 舵机** | **`drv_servo_pwm.c`**  | 负责角度到脉宽的线性映射。                                   |
| **总线舵机** | **`drv_servo_bus.c`**  | 负责串口协议打包（如 STS/SCS 协议），处理多圈模式、温度读取。 |
| **步进电机** | **`drv_stepper.c`**    | 负责角度到脉冲数的转换，甚至包含细分驱动逻辑。               |
| **无刷云台** | **`drv_gimbal_foc.c`** | 负责FOC控制、PID闭环、姿态解算（这里才涉及到动力学 `dyn_`）。 |

### 2. 怎么把它们“合”起来？

你看，虽然文件拆得很散，但在应用层看来，它们都是一个东西。

**代码结构示意：**

```
// 1. 通用的插值器 (model_trajectory.c)
// 这里的逻辑对所有电机都一样
float interp_pos = calc_trapezoidal_trajectory(start, end, speed, accel, time);

// 2. 不同的驱动实现 (drv_xxx.c)

// 情况 A: PWM 舵机
// 它的 set_angle 实现是: PWM_Duty = angle * ratio + offset;
drv_pwm.set_angle(interp_pos); 

// 情况 B: 步进电机
// 它的 set_angle 实现是: Step_Pulse = (angle - current_angle) * steps_per_deg;
drv_stepper.set_angle(interp_pos);

// 情况 C: 总线舵机
// 它的 set_angle 实现是: UART_Write(0x01, 0x05, (int)angle);
drv_bus.set_angle(interp_pos);
```

### 3. 特殊情况：无刷云台

你可能注意到了，无刷云台和其他的完全不一样。PWM/步进/总线舵机通常是“位置开环”或者“内部闭环”，你给位置它就走。

但**无刷云台**是典型的“动力学模型”应用场景：

- 它需要知道 IMU 数据（姿态反馈）。
- 它需要 PID 算法（不仅是规划，还有稳定）。
- 它需要力矩输出。

对于无刷云台，建议单独建立一个文件夹或模块：

- `gimbal_controller/`
  - `ctrl_pid.c` (PID控制算法)
  - `filter_kalman.c` (姿态滤波)
  - `drv_gimbal_foc.c` (驱动实现)
