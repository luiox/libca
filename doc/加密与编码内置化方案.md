# 加密与字符编码内置化方案

> 状态：方案（未实施）。范围：`libca/crypto` 与 `libca/str` 两个模块的依赖策略与演进路线。
> 原则：**零依赖优先、可选增强、双实现对拍**——默认构建不依赖 OpenSSL / iconv / ICU，
> 外部库只作为可选后端，且内置实现永远保留（用于无外部库构建、与外部实现交叉验证）。

## 背景与动机

Java、Go 等语言的惯例是：常见字符编码转换与常用加密原语随标准库内置，不需要用户
额外安装 OpenSSL/ICU 这类"大而全"的重依赖；实际常用的算法集合很小
（base64 / AES / HMAC / HKDF / ed25519 这个量级），mbedtls 这类轻量实现已经证明
内置成本完全可控。

libca 现状的两个痛点：

1. **编码**：`str::CharsetConverter` 的 POSIX 实现依赖 iconv——裁剪版 glibc
   （Alpine、交叉编译环境）常缺 GBK gconv 模块，此时 GBK 转换直接返回
   `UNIMPLEMENTED`；Windows 实现依赖系统代码页。同一份代码在不同环境行为不一致，
   可用性受环境摆布。
2. **加密**：crypto 已内置哈希族与 ChaCha20，但缺 AES / SHA-512 / HKDF / PBKDF2 /
   Poly1305-AEAD / ed25519。若这些算法只提供 OpenSSL 路线，"必须装 OpenSSL"就会
   变成硬依赖，与轻量目标冲突。

## 一、字符编码内置化（str 模块）

### 1.1 三层结构

| 层 | 内容 | 依赖 | 策略 |
|----|------|------|------|
| Tier 1 | UTF-8 ↔ UTF-16LE/BE ↔ UTF-32LE/BE、ASCII、ISO-8859-1、Windows-1252 | 无（纯算法 + ≤32 项差异表） | 始终内置 |
| Tier 2 | GB18030（⊇GBK/GB2312）、Big5、Shift_JIS、EUC-KR；ISO-8859-x / windows-125x 单字节族 | WHATWG encoding 标准 index 表（uint16 双表，代码生成） | 构建期可选嵌入 |
| Tier 3 | 其余长尾编码 | iconv | 可选回落，不引入 ICU |

要点：

- Tier 2 的 DBCS 表从 **WHATWG encoding 标准 index** 生成（encoding_rs、
  Go x/text、Chromium 同源）：每个双字节编码一张"码→码点"表 + 一张"码点→码"表，
  各 40~100 KB；单字节族每编码仅 128 项。生成脚本（python）放 `tools/`，
  **生成物 `.inc` 入库**——构建不依赖网络与 python。
- GB18030 建议默认嵌入（中文场景刚需，且直接替换掉现有 iconv GBK 路径），
  其余 DBCS 由构建开关 `--with_charset_tables=<list|all|none>` 控制。

### 1.2 后端选择

`CharsetConverter` 门面 API 不变，实现层改为三级查找：

```
内置表（Tier 1/2）→ iconv 回落（Tier 3，若启用）→ UNSUPPORTED 错误
```

新增能力查询：`CharsetConverter::supported(charset)` / `list_supported()`。

收益：

- GBK 转换在裁剪 glibc / Alpine / MSVC 上行为一致，现有
  "glibc 接受非法宽字符"这类受 gconv 版本影响的用例（见 commit 2d005cb）可用
  固定向量跨平台断言；
- iconv 从"必需"降级为"长尾兜底"，`--with_iconv=n` 可得纯内置构建。

### 1.3 工作量估计

- Tier 1：1~2 天（UTF 家族部分可复用 `utf8_util` 已有能力）。
- 表生成脚本 + GB18030 集成 + 向量测试：2~3 天；其余 DBCS 每个约 1 天；
  单字节族整体半天。

## 二、加密内置化（crypto 模块）

### 2.1 现状盘点

已有：SHA-256 / SHA-1 / MD5 / SHA-3、HMAC-SHA256、ChaCha20（RFC 8439 块函数 +
XOR）、Base64 / Hex、CRC、`secure_random`、`constant_time_eq`、`secure_zero`
（Windows 已链 bcrypt，CNG 可用）。

缺口（按用途排序）：HKDF / PBKDF2（密钥派生）→ SHA-512（ed25519 前置、
HMAC-SHA512）→ AES-CBC（文件加密与协议兼容）→ Poly1305（→ AEAD）→
X25519 / ed25519（密钥交换 / 签名）。

### 2.2 分期实施

| 期 | 内容 | 规模 | 说明 |
|----|------|------|------|
| P0 | HMAC-SHA1/SHA512、HKDF（RFC 5869）、PBKDF2-HMAC-SHA256（RFC 8018） | 合计 <1 天 | 全部基于已有原语的组合件，几十行一个 |
| P1 | SHA-512 / SHA-384 | ~1 天 | ed25519 前置；结构照 sha256 现有实现 |
| P1 | AES-128/192/256 ECB/CBC/CTR 内置参考实现 | 2~3 天 | 表驱动 ~500 行；**文档明示不承诺常量时间**（威胁模型：本地数据加密与协议互操作，非智能卡场景） |
| P2 | ChaCha20-Poly1305 AEAD（RFC 8439） | 1~2 天 | Poly1305 ~150 行 + AEAD 构造，与已有 chacha20 拼装；无查表、常量时间友好，比 AES-GCM 更适合内置 |
| P2 | X25519（RFC 7748） | ~2 天 | ~200 行域算术；配 HKDF + AEAD 即为完整 Noise 协议积木 |
| P3 | ed25519（RFC 8032） | 1~2 周 | 最大件；可拆"verify 先行"（约 60% 工作量即可验证外部签名） |

**明确不做**：RSA（需大数库与 padding 体系，需要时走 OpenSSL 后端）、
DES/3DES（过时）、RC4 新用途（现有实现标记 deprecated 保留兼容）。

### 2.3 后端架构

```
ca::crypto 门面 API（不变）
├── detail/builtin/   参考实现（始终编译，零依赖）
├── detail/openssl/   EVP 后端（--with_openssl=y 时 AES/GCM 切换到它）
└── detail/cng/       Windows BCrypt 后端（--with_cng，默认开；bcrypt 已链接）
```

- 门面函数与错误模型不变（`Result<T, CryptoError>`，自由函数风格，
  参照 `chacha20.hpp`）；新增错误码：`AUTH_FAILED`（AEAD 标签校验失败）、
  `UNSUPPORTED_ALGORITHM`。
- AES-GCM 只提供 OpenSSL/CNG 后端，内置不实现 GHASH（务实取舍）。
- 算法取舍：签名用 ed25519、密钥交换用 X25519、认证加密用
  ChaCha20-Poly1305（内置）或 AES-GCM（外部后端）、口令派生用 PBKDF2 →
  这套组合覆盖桌面工具类应用的绝大多数真实需求，且全部有 RFC 级测试向量。

### 2.4 测试策略（双实现对拍是本方案的长期正确性保障）

1. 所有内置实现跑 RFC/NIST 官方向量：HMAC（RFC 4231）、HKDF（RFC 5869 附录）、
   PBKDF2（RFC 6070 等）、AES（FIPS-197 / SP 800-38A）、ChaCha20-Poly1305
   （RFC 8439 §2.6/§2.8/附录 A）、X25519（RFC 7748 §5.2）、ed25519（RFC 8032 §7.1）。
2. `--with_openssl=y` / `--with_cng` 时增加**内置 vs 外部后端**交叉对拍测试：
   同输入比输出，防止两套实现漂移。
3. 向量数据以 `.inc`/测试数据文件入库，测试不依赖网络。

### 2.5 与 libca.em 的协同

P0~P2 的内置实现按"可移植核心算术 + 薄 C++ 封装"组织（无平台依赖、
不依赖 heavyweight STL），后续可平移为 C99 供 `em_crypto` 复用
（mbedtls 同款路径）；RFC 向量测试两端共享。

## 三、构建开关汇总

| 开关 | 默认 | 作用 |
|------|------|------|
| `--with_openssl` | n | AES/GCM 走 OpenSSL EVP；同时启用双实现对拍测试 |
| `--with_cng`（新） | Windows 默认 y | AES/GCM 走 BCrypt |
| `--with_charset_tables`（新） | gb18030 | 嵌入哪些 DBCS 编码表（list/all/none） |
| `--with_iconv`（新） | POSIX y | iconv 兜底后端；n = 纯内置构建 |

目标形态：**默认配置零第三方依赖、GBK 跨平台可用**；需要性能或合规背书时
打开 OpenSSL/CNG，且两套实现始终互相对拍。

## 四、落地顺序建议

1. P0 组合件 + SHA-512（一周内，纯加法零风险）；
2. 字符编码 Tier 1 + GB18030 表（解决 iconv 现役痛点，收益最直接）；
3. AES 内置 + 后端选择骨架（把 `--with_openssl` 的后端切换机制立起来）；
4. ChaCha20-Poly1305、X25519；
5. ed25519（可拆 verify 先行）。
